## 3. Data boundaries (ERD → ownership)

### 3.1 Rules

1. **One owner per table.** Only the owning module's repositories write its table. Other modules call the owner's public service (§4). Reads across modules also go through the owner's service. There are no cross-module joins in repository code; the only exception is a read-only query the owner exposes as a public method.
2. **Foreign keys point down the layer graph (§4.1).** A child table may reference a parent owned by the same module or by a module in a lower layer. The child's owner declares the foreign key and its delete rule. A module never references a table in a higher layer. Where a higher layer needs to link to a lower row, the higher-layer row holds the FK (for example `drafts.product_media_id` → `media_objects`).
3. **Delete behaviour.** User-owned rows cascade from `users` (account removal, erasure step 5 hard-deletes the `users` row, §3.4 SB-D12) and campaign-owned rows cascade from `campaigns` (campaign hard delete). Personal data with no FK to `users` (`invitations`, `access_requests` addressed to the subject) is erased explicitly by identity in the same step (SB-D12). A cascade declared by a child's owner is how that owner consents to the delete. **History tables have no foreign keys** (`usage_events`, `audit_events`, `key_events`, `claim_events`, `admin_alerts`): they hold plain UUID columns and outlive their subjects (ARCH-G1 §5.5, SAR3-03).
4. **Authorization column.** Every user-owned table that an API operation addresses by its own ID or lists has `owner_id uuid not null`. Every list index leads with `owner_id`. Every repository method takes `owner_id` from the actor context (ARCH-G1 §7.1). **Exemption:** `brief_segments` and `assembly_clips` have no `owner_id`. They are child rows reached only through an owner-checked parent in the same module (`briefs`, `assembly_jobs`), by a same-module join, and no operation addresses them by their own ID. `claim_issues` carries `owner_id` because API-054 addresses it directly.
5. **Identity and time.** UUIDv7 primary keys, generated by the application. `timestamptz` in UTC. `created_at` and `updated_at` on every mutable table. Optimistic `version int` on `drafts`, `briefs` and `users` (409 on a mismatch).
6. **States are CHECK constraints** with the exact values below. Changing a state set is a boundary change (§8).
7. **No soft-delete flags.** `campaigns.state = 'deleting'` is the only hidden state, and it lasts only while a deletion run is active (CR-02).

### 3.4 Decisions settled at the data boundary

- **SB-D1 Draft → campaign.** Submitting a draft creates the campaign and sets `drafts.campaign_id`, in one transaction, under the unique index. A second submit returns the same campaign (REQ-005 "no second generation"). The Drafts tab lists drafts with `campaign_id is null`. The draft row is deleted with its campaign (CASCADE). A submitted draft is frozen (SB-D13).
- **SB-D2 Media ownership and lifetime.** Every stored R2 object has one `media_objects` row: uploads, clips, finals and thumbstoppers. That makes the storage quota one sum. Uploads are stored at `u/{userId}/media/{mediaId}`. Outputs are stored at `u/{userId}/c/{campaignId}/…`. `campaign_id` is a plain UUID because `media` sits below `campaigns`. An upload becomes attached when a draft references it (`media.attach(mediaId)`); on draft submit, `media.attach(mediaId, campaignId)` also sets its `campaign_id`. An upload belongs to one draft or campaign only; attaching it to a second one is refused (409 `state_conflict`). An upload left **unattached for 24 hours** (configurable `MEDIA_UNATTACHED_TTL`) is deleted by the media sweep. Campaign deletion deletes the campaign's media rows by `campaign_id` and its product image, then sweeps the campaign prefix, in the order fixed by SB-D17.
- **SB-D3 Lifecycle orchestration module.** Campaign deletion, suspend, reinstate, account removal and erasure move from `campaigns` and `identity` into a top-layer `lifecycle` module (§4). This removes the cycle in the ARCH-G1 §4 graph: `campaigns.deleteCampaign` needed `production`, and `production` depends on `campaigns`. `identity` keeps users, the actor context and `assertAdminInvariant()`. `lifecycle` calls them.
- **SB-D4 Provider job tables.** Each owning module keeps its own job table (`brief_jobs`, `video_jobs`, `qc_runs`, `thumbstopper_jobs`) with the shared column contract in §3.5. `platform/jobs` supplies the at-most-once state machine over that contract (ARCH-G1 §5.4). A single shared jobs table was rejected, because it would split each job's domain fields from its state.
- **SB-D9 Usage event for every provider call (closes SAR-G1-L3).** Every provider call writes exactly one `usage_events` row, unique per `(job_type, job_id, call_seq)`, in the same transaction that replaces the reservation. A success records the estimate (`cost_basis='estimate'`). A **definitive, unbilled rejection** records `outcome='rejected'` at **zero cost** (`cost_basis='zero_rejected'`). That covers a 4xx with no task ID and no accepted work, including 401 and 429; it still counts for the REQ-021 report. An unknown outcome (orphaned `submitting`, or cancelled while `submitting`) records the estimate as `unconfirmed`. A later provider response confirms that row, and an insert on conflict does nothing. A 5xx or a timeout after the request was sent is an unknown outcome, not a rejection.
- **SB-D10 Caps and price table are configuration.** The spend caps (`SPEND_CAP_DAILY_USD`, `SPEND_CAP_MONTHLY_USD`, OI-CAPS) are configuration, as are the other thresholds. No per-user override exists and the PRD asks for none. The price table is a versioned file in the repository, `config/price-table.json`, loaded into `price_table` by the release seed and changed by a reviewed PR. This meets REQ-019 and REQ-021 ("configured price table") without an admin editing surface the PRD does not ask for.
- **SB-D11 Brief segment identity and the out-of-date contract (fixes SAR-SB-H1).** (a) `brief_segments` rows are **stable**: one row per `(brief_id, position)`, inserted when a position first appears in a generated brief, **updated in place** by edit (API-051) and regenerate (API-053), and deleted only by the `briefs` cascade from a campaign hard delete. If a regenerate returns fewer segments, the extra positions become `state='retired'` (text cleared, revision incremented); a later regenerate that needs them again sets them back to `active`. `video_jobs.segment_id` is NO ACTION, so the database itself refuses any other delete of a segment that has jobs, and no paid clip, QC run or assembly clip is ever lost to a segment rewrite. (b) **Boundary column:** `brief_segments.revision int not null default 1`, incremented in the same transaction whenever the segment's `prompt`, `dialogue` or `state` changes. Production calls `brief.segmentForProduction(campaignId, position)` → `{segmentId, revision, state, prompt, dialogue}` when it creates a video job and stores `video_jobs.segment_revision`. A video job is **out of date** when `video_jobs.segment_revision < brief_segments.revision`, computed at read by production through `brief.segmentRevisions(campaignId)` → `[{position, segmentId, revision, state}]`. Nothing in `brief` writes a production table. An assembly is out of date (REQ-011) when any of its clips is out of date, or when a newer `completed` video job exists for a clip's segment; API-071 and API-061 return these derived flags. The reuse hash includes the prompt text (ARCH-G1 §5.3), so a changed segment never reuses an old job. (c) **Brief state on change:** an edit or a regenerate of an `accepted` brief moves it back to `draft` (`accepted_at` cleared) in the same transaction, and the claim rules re-run. New segment jobs (API-060) need `accepted` and otherwise return 422 `brief_not_accepted`, so only reviewed copy reaches production (REQ-008). Jobs already running or completed are not cancelled; they continue and are shown out of date. Edit and accept while the brief is `generating` return 409 `state_conflict`. A regenerate moves the brief to `generating`, then to `draft` on success or `failed` on failure. Whichever happens, existing segment rows keep their text until the new result is written.
- **SB-D12 Account erasure (fixes SAR-SB-M1).** Erasure step 5 (ARCH-G1 §5.3) **hard-deletes the `users` row**. There is no tombstone. In one transaction, `lifecycle` reads the subject's `email` and `idp_subject`, calls `identity.eraseSubjectRecords(userId)`, then deletes the user. That call deletes `invitations` where `lower(email)` matches, and `access_requests` where `idp_subject` or `lower(email)` matches. The `users` delete then cascades to every user-owned table (rule 3). `invitations.invited_by` on rows the subject sent as an admin is SET NULL; those rows hold the invitee's data, not the subject's. From removal until step 5 the row exists with `status='removed'`, and API-100 shows it with its erasure step. After step 5 the account appears only in `deletion_runs` (IDs only), which `lifecycle` exposes through API-105. Audit, usage, key and claim events keep the user ID as plain UUIDs (rule 3, OI-RET).
- **SB-D13 Submitted drafts are frozen (fixes SAR-SB-M3).** For a draft with `campaign_id` set, API-023 (PATCH) and API-025 (DELETE) return 409 `state_conflict`. API-024 returns the same campaign and brief job as the first submit (the idempotent replay, with or without an Idempotency-Key). API-022 returns the draft read-only with its `campaign_id`. A submitted draft's product image is deleted only through the campaign deletion path (SB-D17). API-025 on an unsubmitted draft deletes the draft and its product image, which by SB-D2 belongs to that draft alone.
- **SB-D17 Output media references and deletion order (fixes SAR-SB-M2).** `video_jobs.output_media_id`, `assembly_jobs.output_media_id` and `thumbstopper_jobs.output_media_id` → `media_objects` **SET NULL**, the same rule as `drafts`/`campaigns.product_media_id`. **Campaign deletion order** (`lifecycle`): (1) API transaction: `campaigns.markDeleting()`, `brief.cancelForCampaign()` and `production.cancelForCampaign()` (non-terminal jobs → `cancelled`), enqueue the deletion run; (2) worker: `media.deleteForCampaign(campaignId)` deletes R2 objects by `storage_key`, then their `media_objects` rows in batches (a row is deleted only after its object is gone, so a retry finds what is left; SET NULL clears output references); (3) worker: `media.sweepPrefix(u/{userId}/c/{campaignId}/)` verification count; (4) worker: `campaigns.hardDelete()` cascades drafts, briefs, segments, claim issues, every job table and assembly clips in one statement. **Account erasure** steps 3–5 follow the same pattern: R2 prefix removal, verification, then the `users` delete (SB-D12) cascades the rows.
- **SB-D15 Request-access form switch (fixes SAR-SB-L5).** Whether the public request-access form is on is configuration, `ACCESS_REQUEST_FORM_ENABLED` (boolean, default `false`, the least exposed choice), set by the deployer through the configuration registry and changed by a reviewed release. It is not a `platform_settings` column and has no write API, the same pattern as SB-D10. API-120 shows it read-only. When it is `false`, API-002 returns 404 and no pending request is recorded.

### 3.5 Provider-job column contract (shared by SB-D4 tables)

`id`, `owner_id`, `state`, `cause_class`, `cause_message`, `reuse_hash`, `key_id` (plain uuid), `key_version`, `submitting_at`, `provider_task_id`, `next_poll_at`, `deadline_at`, `provider_completed_at` (v4.1), `created_at`, `updated_at`.

- `deadline_at` bounds the provider's work only. Once the provider reports completion, `provider_completed_at` is set (state stays `processing` while the output is copied) and the deadline no longer applies; the free copy has its own window (AIU-13 `architecture` §5.5, `PROVIDER_OUTPUT_COPY_WINDOW_HOURS`).

- States: `pending | submitting | submitted | processing | completed | failed | cancelled`. Synchronous OpenAI calls skip `submitted` and `processing` (ARCH-G1 §5.3).
- User labels: `pending` → pending (or "queued" when the running limit holds it); `submitting`, `submitted` → created; `processing`; `completed`; `failed` and `cancelled` → failed with a cause.
- Cause classes: `temporary | configuration | credit | provider_timeout | key_replaced | key_deleted | reference_unreachable | output_unreachable | outcome_unknown | cancelled_campaign_deleted | cancelled_account_suspended | cancelled_account_removed`.
- Reuse: a partial unique index on `(owner_id, reuse_hash)` over states not in `failed` and `cancelled`; the hash covers the job type and its parent IDs (v3: `brief_jobs` has two parent kinds). `assembly_jobs` keeps `(campaign_id, reuse_hash)`.
- States move forward only. A failed or cancelled row is never revived; Retry inserts a new row.

### 7.1 Backup identity (v4, SB-D18..SB-D21; v5 fixes SB-D22..SB-D25)

The backup identity is everything the daily `backup` cron service (DEVOPS-PLAN §5.1, §10.3) uses. It exists to produce an independent logical dump and a media and ledger copy. It reads everything, so it is scoped so that it can **read and add copies, and nothing else**: it cannot change application data, cannot destroy a backup inside the retention window, and cannot open the key ciphertext it copies.

**A. Service and image.**

| Item | Boundary decision |
| --- | --- |
| Service name | `backup`: Render cron job, one per environment, daily, **no inbound port**, egress only to the environment's PostgreSQL (private network), the R2 endpoint and the heartbeat host |
| Image | Only the `backup` target of `docker/Dockerfile` (PostgreSQL client of the server's major version, `age`, an S3 client, the copy script). **No application code**: no `apps/api` modules, no `ops-cli`, no unsealer, no Drizzle, no pg-boss. It never runs the `api`, `worker` or `web` image, and no other service runs the `backup` image |
| Media handling | Byte copy only. It never decodes, transcodes or parses an object (consistent with SEC-D SR-01) and copies only the `u/` prefix (sanitized media), never `q/` (quarantine) or `smoke/` |
| Connections | One database connection per run (`pg_dump` without `-j`); role connection limit 2 (§B) |
| Schedule rule | It does not run while a release migration runs (`pg_dump` takes ACCESS SHARE locks). The release job's own pre-migration backup (DEVOPS-PLAN §10.1) is the host's on-demand backup or a release-step dump, not this service |

**B. PostgreSQL role `app_backup`.**

| Attribute or grant | Value | Why |
| --- | --- | --- |
| Role attributes | `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION NOBYPASSRLS CONNECTION LIMIT 2` | Least privilege. No replication: a logical dump does not need it |
| Membership | **Member of no role.** In particular not of `app_api`, `app_worker`, `app_migrator`, the host's admin role or any predefined role (`pg_read_all_data`, `pg_write_all_data`, `pg_monitor`, `pg_read_server_files`, `pg_execute_server_program`, `pg_signal_backend`). **Members of `app_backup`:** only the host admin role that created it, and only with the grant PostgreSQL 16+ makes automatically for a non-superuser `CREATEROLE` creator, held as `ADMIN OPTION` with `INHERIT FALSE` and `SET FALSE` (`createrole_self_grant` left empty). No other role is a member, and no member may inherit or `SET ROLE` to it | A membership would inherit write or DDL rights or reach the server file system. Explicit grants are reviewable and limited to two schemas (SB-D19). The admin-only grant lets the host admin rotate the password and drop the role without gaining its read rights; revoking it on a managed host would lose that ability (SB-D25) |
| Session defaults | `ALTER ROLE app_backup SET default_transaction_read_only = on`; `idle_in_transaction_session_timeout` and `statement_timeout` sized to the dump (DevOps records the values at DO-05, like the other roles) | A second guard if a grant is ever too wide |
| Database | `CONNECT` on the application database, granted by the host admin at DO-11 (`app_migrator` may not own the database, so M0001 does not grant it). PostgreSQL gives `PUBLIC` `CONNECT` on every database by default; where the host allows, DevOps revokes `CONNECT FROM PUBLIC` on the environment's other databases at DO-11, and otherwise records that `app_backup` can connect to them but holds no grant there | Connecting to another database exposes only its catalog, because every object grant is in the application database (SB-D25) |
| Schemas | `USAGE` on `public` and `pgboss` only. No `CREATE` on any schema | Schemas from AIU-13 §2.10. pg-boss state is part of the restore (queued jobs) |
| Tables | `SELECT` on every table in `public` and `pgboss`, **all columns, including `provider_keys.ciphertext`, `nonce` and `wrapped_dek`** | The dump must be complete for the restore to work. Ciphertext is useless without a `KEK_V{n}` private key, which this identity never holds (§D, T-01, KC-1) |
| Sequences | `SELECT` on every sequence in both schemas (`pg_dump` reads `last_value`). No `USAGE` or `UPDATE` | — |
| Future objects | `ALTER DEFAULT PRIVILEGES FOR ROLE app_migrator IN SCHEMA public, pgboss GRANT SELECT ON TABLES TO app_backup` and the same `ON SEQUENCES` | New tables are dumped without a manual step. Default privileges cover **only objects `app_migrator` creates**, so the rule below is part of this boundary |
| pg-boss DDL (v5, SB-D24) | **All pg-boss DDL runs under `app_migrator` in the release step `jobs:migrate`:** the schema install and upgrade **and `createQueue` for every queue** (pg-boss 10+ creates per-queue tables or partitions in `pgboss`). The queue list is in code and `jobs:migrate` creates any missing queue. The api and worker start pg-boss with schema migration off and never call `createQueue`; they have no `CREATE` on `pgboss`, so an attempt fails closed at startup instead of creating a table `app_backup` cannot read | Otherwise a queue created at runtime by `app_worker` or `app_api` gets no `SELECT` for `app_backup`, `pg_dump` fails with "permission denied", and nobody learns of it until ALR-6 after 26 h. AIU-13 records this in its pg-boss and `jobs:migrate` design |
| Refused (tested) | INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER on any table; any DDL; `SET ROLE` to any role; `COPY ... TO PROGRAM` or to a server file; `pg_terminate_backend` | Grants test in the migration ticket (§E) |
| Row-level security | **Not needed and not granted (`NOBYPASSRLS`)**. ADR-009 adopts no RLS, so `pg_dump` (which sets `row_security = off`) reads every row | If RLS is ever adopted (SEC-D §7 conditions), `pg_dump` under this role fails instead of producing an incomplete dump; giving `app_backup` `BYPASSRLS` is then a §8 boundary change decided with that RLS change, never a silent addition |
| Who creates it | The role is created per environment at provisioning (DO-11) by the host's admin user; the password is generated there and stored only in the `backup` service environment. The grants and default privileges are issued by `app_migrator` in migration **M0001** (platform), so the migration history records them | One migration owner (§1). The role exists before M0001 runs; the migration fails closed if it is missing |
| Env var | `BACKUP_DATABASE_URL` (not `DATABASE_URL`, so no app code path can pick it up), TLS as AIU-13 §2.10 | — |

**C. R2 tokens and buckets.** Cloudflare R2 API tokens take one permission level per token (Object Read only or Object Read & Write) and scope to buckets, not prefixes or verbs (SEC-D R-3, VERIFY at DO-07 against the account). "Read the app bucket, write the backup bucket" therefore needs **two tokens**, and "no delete, no overwrite" is enforced by the **backup bucket's lock rules**, not by the token (SB-D20).

| Item | Boundary decision |
| --- | --- |
| Buckets per environment | `app` (existing, prefixes `q/`, `u/`, `smoke/`), `erasure-ledger` (new, SEC-D §10.8, SB-D21), `backup` (new). Actual names are DevOps's (DOP-OI-5); each is in the environment's own account scope, so a staging token cannot reach production |
| `R2_BACKUP_SOURCE_ACCESS_KEY_ID` / `R2_BACKUP_SOURCE_SECRET_ACCESS_KEY` | **Object Read only**, scoped to that environment's `app` and `erasure-ledger` buckets. Cannot put, delete or change any object there |
| `R2_BACKUP_SINK_ACCESS_KEY_ID` / `R2_BACKUP_SINK_SECRET_ACCESS_KEY` | **Object Read & Write**, scoped to that environment's `backup` bucket **only**. No access to `app` or `erasure-ledger`. Not an Admin token, so it cannot change the bucket's lock or lifecycle rules |
| Backup bucket layout | `db/<yyyy-mm-dd>/<ulid>.dump.age` (age-encrypted custom-format dump); `media/<source key>/<source etag>` (content-addressed, so a changed source object is a new key and nothing is overwritten); `manifests/<yyyy-mm-dd>.json` (key, etag, owner id, `deletedAt`); `media-deleted/<yyyy-mm-dd>/<source key>/<source etag>` (v5: copy of a deleted source's media, dated when the deletion was detected); `ledger/<source key>` (ledger mirror) |
| No overwrite | Every write uses a new key and a conditional put (`If-None-Match: *`, VERIFY R2 support at DO-07). The bucket lock below also refuses an overwrite inside the retention |
| How the lock works | An R2 age-based lock rule counts from the moment **the object was uploaded**, not from any date the service records (such as a manifest `deletedAt`). After that age the sink token, which has Object Read & Write, can delete the object. An indefinite rule refuses deletes until an Admin removes the rule. Rules can target a prefix. All lock rules are set by the owner's Admin credential at provisioning, never by the service (VERIFY at DO-07: prefix rules, indefinite retention, and that an in-bucket copy is a new upload for the lock) |
| Lock rules (v5, SB-D23) | (1) **`ledger/`: indefinite retention.** Ledger mirrors can never be deleted with the sink token; changing that is an OI-RET decision that an Admin applies. (2) **Whole bucket: age `BACKUP_RETENTION_DAYS`** (default 30), which covers `db/`, `manifests/`, `media/` and `media-deleted/` |
| Delayed delete of media (v5, SB-D23) | When the manifest shows that a source object was deleted, the next run makes a **server-side copy** of its `media/<source key>/<source etag>` copy to `media-deleted/<deletion-detected date>/<source key>/<source etag>`. That is a new upload, so its lock clock starts at deletion and the only remaining copy is protected for the full `BACKUP_RETENTION_DAYS`. Only after a HEAD confirms the new object (same size and etag) does the service delete the old `media/` copy. **This is the only delete the service performs.** It never deletes in `db/`, `manifests/`, `media-deleted/` or `ledger/` |
| Expiry | Lifecycle rules (Admin-configured, not the service) expire `db/`, `manifests/` and `media-deleted/` after `BACKUP_RETENTION_DAYS` + 1 days. No lifecycle rule on `media/` (live copies, removed only by the step above) or `ledger/` |
| Residual (recorded, for Cybersecurity) | A stolen sink token can delete: (a) a `media/` copy uploaded more than `BACKUP_RETENTION_DAYS` ago. If its source still exists, the source is untouched (no write on `app`) and the next run re-copies it. If its source was deleted **after the last successful run**, that copy is the only copy until the next run moves it to `media-deleted/`, so the exposure window is the time between the source's deletion and the next successful run (normally under 24 h; longer only while runs fail, which raises ALR-6 at 26 h); (b) `db/`, `manifests/` or `media-deleted/` objects older than `BACKUP_RETENTION_DAYS`, which lifecycle expires within one more day anyway. It **cannot** delete or overwrite any object younger than `BACKUP_RETENTION_DAYS`, any `media-deleted/` copy within `BACKUP_RETENTION_DAYS` of its source's deletion being detected, or any `ledger/` object. Residual (a) is routed through the Orchestrator to Cybersecurity (AIU-17) to accept or tighten; it is not accepted by this document |
| If the lock is unavailable | If DO-07 finds R2 bucket locks unavailable on the account, "no delete inside retention" is not met: DevOps records it as a blocking finding against DO-07 and routes it to Cybersecurity through the Orchestrator. It is never accepted silently |

**D. What the backup identity must never hold or reach.** None of these may be in the `backup` service environment, image, build arguments or logs, and a startup check in the backup script refuses to run if any of their names is set (DO-07 test):

- any `KEK_V{n}` private key, `KEK_PRIVATE_KEYS`, a sealed KEK copy or a KEK custody location (KC-1.2: custody locations must not be readable with backup credentials);
- the **age private key** (it holds only the public recipient `BACKUP_AGE_RECIPIENT`; the private key is escrowed under DEVOPS-PLAN §10.4, so the identity can write backups it cannot read back);
- the `app_api`, `app_worker` or `app_migrator` credentials (`DATABASE_URL`, `MIGRATION_DATABASE_URL`) or the host admin database credential;
- R2 token A (`R2_ACCESS_KEY_ID` of the api), token B (worker), token C (ledger writer), or any R2 Admin token;
- signing and session secrets: `CLERK_SECRET_KEY`, `HMAC_PEPPER`, `CURSOR_SIGNING_KEY`, `RATE_LIMIT_IP_KEY`, `METRICS_TOKEN`, any provider or Shotstack key;
- deployment credentials: `RENDER_API_KEY`, `GHCR_PULL_TOKEN`, `SENTRY_AUTH_TOKEN`, GitHub tokens.

It may hold only: `BACKUP_DATABASE_URL`, `R2_BACKUP_SOURCE_*`, `R2_BACKUP_SINK_*`, `BACKUP_AGE_RECIPIENT`, `HEARTBEAT_URL_BACKUP`, and non-secret config (`R2_ENDPOINT`, the three bucket names, `BACKUP_RETENTION_DAYS`). Custodians of the KEK copies are not holders of these credentials (KC-1.2).

**E. Tests that follow (owners in §9).** Grants test (AIU-13 migration ticket M0001, QA traceability): `app_backup` can `SELECT` every table including `provider_keys.ciphertext`; every write, DDL, `SET ROLE`, server-file and program `COPY` is refused; `pg_has_role('app_backup', r, 'MEMBER')` is false for every other role; `pg_auth_members` for `app_backup` has exactly one row, the creating admin role, with `admin_option` true and `inherit_option` and `set_option` false (PostgreSQL 16+); a table added by a later migration is readable without a new grant; **a queue created the way the release step creates it (`jobs:migrate` under `app_migrator`), followed by a `pg_dump` as `app_backup`, succeeds**; `createQueue` and pg-boss schema migration as `app_worker` and `app_api` are refused; `pg_dump` with `--enable-row-security` off completes. R2 test (DO-07): source token cannot put or delete in `app` or `erasure-ledger`, and cannot reach `backup`; sink token cannot reach `app` or `erasure-ledger`; delete and overwrite of a fresh `backup` object are refused; delete of a `ledger/` object of any age is refused (indefinite rule); a server-side copy into `media-deleted/` gets a fresh lock clock; a forbidden variable name stops the service. Restore drill (DEVOPS-PLAN §10.3) restores from these artifacts with the escrowed age key, which proves the identity's output is usable while it cannot read it.

Process placement: api serves every `API-` operation. The worker runs every provider handler, sanitizing, FFmpeg, deletion and erasure steps. It has no inbound port. The api never holds the KEK private key.
