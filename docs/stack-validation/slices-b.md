### FFmpeg concat of four 15 s 1080x1920 clips (F-ASM, NFR-11)

Fixtures: four distinct 15 s 1080x1920 30 fps clips with audio (`testsrc2`, `smptebars`, `mandelbrot`, `rgbtestsrc` plus a sine tone), H.264 and AAC. Render: concat demuxer, `scale=1080:1920,fps=30,format=yuv420p`, `libx264 -preset veryfast -crf 23`, AAC 128 kb/s, `+faststart`; the output is verified as 60 s, H.264 1080x1920 30 fps, AAC. Spawned with an argument array and no shell. Peak RSS is `VmHWM` of the ffmpeg process read from `/proc` every 25 ms.

| Run                                               | Wall time | Peak RSS | Output  |
| ------------------------------------------------- | --------- | -------- | ------- |
| All 4 host cores                                  | 12.1 s    | 408 MB   | 34.0 MB |
| 1 vCPU (`taskset -c 0`), the Standard worker size | 34.5 s    | 255 MB   | 34.0 MB |

The G1 §8.1 estimate is 10 to 60 s. Both runs fall inside it, and the 1 vCPU run (34.5 s) is about 6 % of the 10 min render limit (F-ASM). Peak RSS is at most 408 MB, so the **Standard worker (2 GB) is confirmed** for the render; there is no case for the 4 GB step on this measurement (the 4 GB size would add cost for no demonstrated need). Over the four runs made while developing the test the wall times were 12.1 to 12.9 s and 34.4 to 34.6 s.

Limits of this measurement, recorded rather than hidden: (a) the host is a 4-core QEMU virtual CPU, not a Render instance; `taskset -c 0` limits the process to one core but not to Render's CPU model or memory cgroup, so the real time on Render Standard is **NOT_RUN** until the worker image runs there (deployment-time item, DO-07) and the figure should be repeated then; (b) the source clips are synthetic test patterns, not Seedance output (real footage with more motion and grain encodes slower, an assumption, not measured: if it were 2 times slower the 1 vCPU render is about 70 s); (c) FFmpeg here is 7.0.2 with GPL components, while ARCHITECTURE §1.11 pins 7.1.x without GPL components (VERIFY build flags). libx264 is GPL, so an LGPL-only build has no libx264 and needs another H.264 encoder (for example OpenH264 or a hardware encoder), which changes speed and size: **the worker-image FFmpeg build and its licence remain an open DevOps item** (DEVOPS-PLAN, DO-07), not decided here.

## Step 8: crypto slice (TC-KEY, foundation form)

`crypto.ts` is the foundation form of `KeyWrapPort` (ARCHITECTURE §1.3, TD-D5).

| Claim                                                                                                                                                                                                           | Result |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| KEK is RSA with a 3072-bit modulus; the wrapped DEK is 384 bytes; nonce 12 bytes; ciphertext is plaintext plus the 16-byte GCM tag and does not contain the plaintext                                           | pass   |
| Nonce, wrapped DEK and ciphertext differ on every seal of the same value                                                                                                                                        | pass   |
| AAD `user_id\|provider\|key_id\|version`: a change to any one of the four fields fails with `UnsealFailed`                                                                                                      | pass   |
| A flipped bit in the ciphertext, the tag, the nonce or the wrapped DEK, an unknown `kekVersion`, and a different KEK all fail with `UnsealFailed`                                                               | pass   |
| The wrapping is OAEP with SHA-256: the worker's private key opens the DEK with `sha256`; `sha1` OAEP is refused; PKCS#1 v1.5 never yields the DEK                                                               | pass   |
| Rotation: a value sealed under `KEK_V1` opens after `KEK_V2` is current, and new seals use `KEK_V2`                                                                                                             | pass   |
| The api binding is `createApiBinding(publicKeys, version)`: a frozen object with `seal` only, no `unseal`, no private key input; a binding without the public key cannot seal. The worker binding adds `unseal` | pass   |
| Empty and 4 KiB values round-trip                                                                                                                                                                               | pass   |

Not proven here, and not claimed: that the api **process** has no private key in its environment (a configuration-validation and deployment fact, TC-KEY on the product code), and the product `UnsealFailed` handling (job fails `configuration`, alert `key_unseal_failed`). The foundation proves that the API surface can be built without an unsealer and that the cryptography behaves as specified.
