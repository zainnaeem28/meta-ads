# TASK-062 evidence

- Commands (`node dist/bin/ops.js <command> --env=<APP_ENV>`, also `pnpm --filter @shroomap/api ops ...`): `first-admin:reopen` (audit `first_admin.reopened`), `keys:disable-all` (audit `key.disabled_all`, key events `disabled_by_operator`, alert `keys_disabled_all`), `kek:rewrap` (audit `kek.rewrapped`, key events `rewrapped`), `erasure:resume <runId>` (audit `erasure.resumed`). All audit events are `actor_type = 'operator'`, no actor id. Output is `name=count` lines only; failures print the error class, never its message.
- Environment guard: `--env=<name>` is mandatory and must equal `APP_ENV`; a mismatch exits 2 before any database connection and writes no audit event (nothing is connected to write it). The connected database name must also equal the one in `DATABASE_URL`. Exit codes: 0 done, 1 incomplete or failed, 2 refused, 78 invalid configuration.
- `kek:rewrap`: one row, one transaction, row locked and re-read; the data key is opened with the private key of the row's `kek_version`, the value must open (AES-GCM with the `user|provider|key|version` AAD) before and the new wrapping must open to the same data key after; only then `wrapped_dek` and `kek_version` are written (ciphertext, nonce and AAD unchanged). `kek_version` is the progress mark, so a killed run or a second run continues with what is left. A row it cannot rewrap is left untouched, counted as `failed`, audited with outcome `failed` and the exit code is 1.
- Role decision (departure from ARCHITECTURE §7.3, which says api role): `erasure:resume` runs under the worker configuration and role, because M0060 grants `app_api` only SELECT, INSERT on `deletion_runs` (the same gap TASK-059 recorded). `kek:rewrap` also needs the worker role (private keys). `first-admin:reopen` and `keys:disable-all` run under the api configuration. A migration granting `UPDATE ON deletion_runs TO app_api` would let the architecture's wording hold; not part of this ticket.
- `erasure:resume` covers both run kinds (account to `lifecycle.account-erasure`, campaign to `lifecycle.campaign-deletion`), enqueued on the transaction that sets the run back to `running`.
- The commands do their own SQL in `platform/ops-cli/commands.ts` over `database/schema/*`: the module services (`ProviderKeysService.disableAll`, `AccountLifecycleService.resume`) are not exported from their module indexes and the layer rule `no-deep-import` forbids reaching them from `platform/ops-cli`. The behaviour (statuses, events, audit, alert) is the same.
- Integration proof: `apps/api/src/platform/ops-cli/ops-cli.integration.test.ts` on real PostgreSQL: `runOps` with the production `executeCommand`; `erasure:resume` then handled by the real worker composition root `createWorkerApp` (ledger object written, run advances); `kek:rewrap` killed after two rows and resumed, then every key opened by the worker's own `KeyUnsealer` holding only the new private key; and the compiled `dist/bin/ops.js` spawned for a mismatch refusal, a real `first-admin:reopen` and a bad command line. Unit tests: `args.test.ts`, `runner.test.ts`, `kek-crypto.test.ts`.
- Files outside the allowed paths that had to change (same wiring as TASK-058 and 059): `apps/api/vitest.config.ts` (the `reports/opscli/junit.xml` reporter, coverage include of `src/platform/ops-cli`, exclusion of the SQL, binding and barrel files that the integration test proves), `apps/api/package.json` (the `reports/opscli/lcov.info` copy and an `ops` script).
- `reports/deps.json` is the merged blocking and recorded findings of `scripts/ci/deps.sh`, built as `rescan.sh` builds it. The ticket's `pnpm --filter @shroomap/api lint typecheck test:unit test:integration` is run as four commands, one script each.
