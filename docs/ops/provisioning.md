# Environment provisioning (DO-11, TASK-018)

Environment configuration as code. The team never provisions, deploys or holds a hosting credential: everything below is a file or a script that was proven **without credentials** (`scripts/provision/plan.sh --check`, evidence `docs/evidence/TASK-018/plan.txt`), and the owner runs it once per environment on their own accounts. Nothing here runs before the environment's G3 (a staging G3 first; a staging G3 never authorizes production). DEVOPS-PLAN 5, 6.1, 10.2, 17 DO-11; SB v6 7.1 B, C.

| Piece                                                  | Where                                                                 | Proven without credentials by                                                                                                                                                              |
| ------------------------------------------------------ | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Render Blueprint per environment (manual sync only)    | `infra/render/<env>/render.yaml`, generated by `render-blueprint.mjs` | lint of every service and variable against `config/registry.json` and `.env.example`, currency check, 15 injected defects each caught                                                      |
| Database roles, `app_backup`, grants, session defaults | `scripts/provision/roles.sh`, `sql/roles.sql`, `sql/verify.sql`       | run twice on a disposable database of the shared test PostgreSQL by a non-superuser `CREATEROLE` admin (as the host does); drift, rotation, elevated role, missing password, read-back, G3 |
| Buckets, lock and lifecycle rules                      | `scripts/provision/buckets.mjs`                                       | apply twice, read back, drift, host errors and the G3 refusal against a local stand-in of the Cloudflare R2 API                                                                            |
| `max_connections` against the 47-connection peak       | `scripts/provision/capacity.json`, read back by `sql/verify.sql`      | the peak recomputed from the pool counts; the read-back fails when a plan cannot hold it within 80%                                                                                        |

## What the Blueprint does and does not do

- One file per environment: 1 PostgreSQL (private, `ipAllowList: []`, a paid tier, version 17), `web` and `api` (web services with a health check), `worker` (background worker, no port, shutdown delay 120 s), `migrate` (private service the release runs one-off Render Jobs on, with the `api` image), `backup` (cron `17 2 * * *`) and `monitor` (cron every 5 minutes).
- `autoDeployTrigger: off` on every service: a push or an image change deploys nothing. Images are deployed by digest through `release.yml` (`docs/ops/release.md`). The Blueprint names the image repository only; it carries no digest and no tag.
- Variable names come from `config/registry.json`: every name a process requires, plus the public values the Blueprint can fix (`APP_ENV`, `SENTRY_ENVIRONMENT`, the three bucket names, `BACKUP_RETENTION_DAYS`, `API_PORT`, `WORKER_DRAIN_SECONDS`). Every secret, and every public value only the owner knows (origins, endpoint, issuer, recipient), is `sync: false`: Render asks for it at the first sync and the value never enters the repository. The backup service holds none of the names in `backupForbidden`; the `migrate` service holds only `MIGRATION_DATABASE_URL`.
- Plans (`PROFILE` in `render-blueprint.mjs`), the region (`frankfurt`) and the image path are the owner's choices (DOP-OI-1, cost estimate DEVOPS-PLAN 13): change the constant or set `PROVISION_IMAGE_PREFIX`, run `scripts/provision/plan.sh --write`, commit. Check with `PROVISION_IMAGE_PREFIX=<same value> node scripts/provision/render-blueprint.mjs --check`.

## Owner runbook (once per environment, in this order)

Prerequisites the owner supplies: a Render account and workspace, a Cloudflare account with R2, the registry path of the images (GHCR), the environment's G3 record (`g3.json`, decision `PASS`, `environment` equal to the target), `psql` 16+ and Node 24. **Credentials stay on the owner's machine**: nothing below is pasted into a ticket, a comment or a file of the repository.

1. **Blueprint.** Regenerate with your image path if it is not the placeholder (`PROVISION_IMAGE_PREFIX=ghcr.io/<owner>/<repo> scripts/provision/plan.sh --write`, commit). In Render choose _New > Blueprint_, point it at `infra/render/<env>/render.yaml`, keep **manual sync**, and sync once. Fill each `sync: false` variable from `docs/ops/secrets.md` (names, classes, owners). `DATABASE_URL`, `MIGRATION_DATABASE_URL` and `BACKUP_DATABASE_URL` are the three role URLs of step 3, using the database's **internal** hostname and `sslmode=require`; Render's default `host_admin` URL is used only by step 3 and is never given to a service. Add the GHCR registry credential to Render (read-only package access).
2. **Buckets.** With the owner's Admin credential:
   ```
   export CLOUDFLARE_ACCOUNT_ID=…  CLOUDFLARE_ADMIN_TOKEN=…      # R2 edit permission; Admin stays with the owner (SB-D23)
   export BACKUP_RETENTION_DAYS=30                                  # same value as the backup service
   export PROVISION_G3_RECORD=./g3.json
   node scripts/provision/buckets.mjs plan   --env <env>           # review the desired state (no network)
   node scripts/provision/buckets.mjs apply  --env <env>           # creates what is missing, sets the rules, reads them back
   node scripts/provision/buckets.mjs verify --env <env>           # read-only; run again at any time
   ```
   It creates `shroomap-<env>-app`, `-erasure-ledger` and `-backup` (private) and sets: lock on `backup` prefix `ledger/` indefinite, lock on the whole `backup` bucket by age `BACKUP_RETENTION_DAYS`, lifecycle expiry of `db/`, `manifests/` and `media-deleted/` after `BACKUP_RETENTION_DAYS` + 1 days, nothing on `media/` or `ledger/`. Then create the five R2 tokens in the Cloudflare dashboard, scoped to one bucket each (tokens are not created by this script, so no token value ever passes through it): A (api) Object Read & Write on `app`; B (worker) Object Read & Write on `app`; C (worker, `R2_LEDGER_*`) write-once and read on `erasure-ledger`; `R2_BACKUP_SOURCE_*` Object Read only on `app` and `erasure-ledger`; `R2_BACKUP_SINK_*` Object Read & Write on `backup` only. None is Admin. Finally prove the lock with the sink token: `node scripts/backup/src/verify-locks.ts` (`docs/ops/backup.md`, TC-H-15).
3. **Roles and grants.** Connect as the database's admin role (Render's `host_admin`, which has `CREATEROLE`) through the external URL for the duration of this step (allow your IP temporarily in Render, then remove it again), and run:
   ```
   export PROVISION_DATABASE_URL='postgres://host_admin:…@<external host>/shroomap?sslmode=require'
   export PROVISION_ENVIRONMENT=<env>  PROVISION_G3_RECORD=./g3.json
   export PROVISION_PW_MIGRATOR=…  PROVISION_PW_API=…  PROVISION_PW_WORKER=…  PROVISION_PW_BACKUP=…     # new, random, at least 24 characters
   scripts/provision/roles.sh apply     # creates the four roles, grants, session defaults, then reads everything back
   scripts/provision/roles.sh verify    # read-only; run again at any time
   ```
   It creates `app_migrator`, `app_api`, `app_worker` and `app_backup`; none is superuser, `CREATEDB`, `CREATEROLE`, replication or `BYPASSRLS`. `app_backup` is `NOINHERIT`, `CONNECTION LIMIT 2`, has `default_transaction_read_only = on`, is a member of no role, and gets `CONNECT` on the application database only; the other three get `CONNECT` and `search_path = public`. The admin's automatic PostgreSQL 16+ membership in each created role (`ADMIN OPTION`, `INHERIT FALSE`, `SET FALSE`, SB-D25) is neither revoked nor widened. `CONNECT` is revoked from `PUBLIC` on the environment's other databases where the admin owns them; where the host does not allow it the read-back prints `RECORDED database <name> still allows CONNECT through PUBLIC` and that line goes into the go-live evidence. Re-running is safe: attributes drift back, passwords stay unless `--rotate` is given (`docs/ops/secret-rotation.md`). The table grants (`SELECT` for `app_backup`, DML for the runtime roles) are M0001's, applied by the release's `db:migrate`; M0001 refuses to run when a role is missing or has other attributes than the ones above. The script prints no password and refuses without the G3 record.
4. **Capacity.** The read-back at the end of step 3 prints `max_connections` and fails when the 47-connection rolling-deploy peak (`capacity.json`: api 8+2, worker 6+6, doubled while old and new overlap, backup 1, operator 2) exceeds 80% of it (a plan needs at least 59). If it fails, shrink the pools (api 5+2, worker 4+4) before G3 and update `capacity.json`. Record the printed value in the go-live evidence.
5. **Release.** Set the GitHub environment secrets and variables of `docs/ops/release.md` and `docs/ops/secrets.md` (`RENDER_API_KEY`, the Render service ids printed by the Blueprint, `RELEASE_IMAGE_PREFIX` equal to the image path above). The first release then runs `release.yml` as documented; it migrates, deploys by digest and observes.

Rollback of this step: nothing here is destructive on re-run; to retire an environment delete the Render project and the three buckets (a locked bucket empties only after its lock age).

## Owner additions, in one list (what is missing until the owner supplies it)

`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_ADMIN_TOKEN`; the five R2 tokens; `PROVISION_DATABASE_URL` and the four `PROVISION_PW_*`; the G3 record per environment; the Render account, API key and registry credential; the image path (`PROVISION_IMAGE_PREFIX`); region, plans and the `max_connections` of the chosen plan. Without them the scripts stop as **deployment-ready, not deployed** (exit 0, no connection made) and the plan check still passes.

## Open VERIFY items and findings (none was checked against a live account)

1. **Cloudflare request shapes.** `buckets.mjs` follows Cloudflare's R2 API for bucket creation, `PUT …/lifecycle` and `PUT …/lock` (rule field names `conditions.prefix`, `deleteObjectsTransition.condition`, `condition.type` `Age` / `Indefinite`). The tests prove the script against a stand-in, not Cloudflare. If a field name differs, `apply` fails at the first request or the read-back differs and the run stops; fix the shapes in `desired()` and rerun. That the host really refuses a delete inside the lock is proven by `verify-locks.ts` (item 2 of step 2), not by this script.
2. **Render Blueprint keys.** Plan names (`basic-1gb`, `pro-4gb`, `starter`, `standard`), `autoDeployTrigger`, `maxShutdownDelaySeconds`, `type: pserv` for `migrate` and the `dockerCommand` that keeps it idle are written from Render's Blueprint specification and unverified until the first sync (DEVOPS-PLAN 6.1; `docs/ops/release.md` VERIFY 2 and 3). The lint is this repository's own and is not Render's validator.
3. **Finding F-1, monitor image.** `monitor` runs the `api` image with `node scripts/monitor/src/main.ts` (DEVOPS-PLAN 5.1), but the `api` Docker target does not contain `scripts/monitor`. The cron is in the Blueprint as planned and will fail until a `monitor` target or the code is added to the image (`docker/` is DO-04's path: change request to the Orchestrator, not done here).
4. **Finding F-2, `max_connections`.** The value of the chosen Render plan is not known to the team; the read-back is the check, run by the owner at step 3.
5. **Finding F-3, CI wiring.** `plan.sh --check` is the ticket's required check and runs in `submit_check.py`. Adding it to `ci.yml` (`.github/workflows/`, outside this ticket's paths) is a change request to the Orchestrator.
