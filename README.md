# ShrooMap AI UGC Ad Director

An internal web application for ShrooMap's marketing and creative team. An operator goes from campaign inputs to a downloadable, brand-checked final ad inside one application: product upload and analysis, a brand-guided brief, video segments generated by an AI provider, audio quality checks and final assembly. Generation costs fall on each user's **own** provider keys (OpenAI and WaveSpeed), which the application stores sealed and never shows again.

The audience is internal ShrooMap staff only: creative operators (`user`) and administrators (`admin`). An anonymous visitor is denied everything. Out of scope: consumer quiz, payments, ad-network publishing, multi-tenant agency accounts (see the PRD for the full list).

> **Status: deployment-ready, not deployed.** The product runs end to end on a local stack with no external account. Hosting, identity, storage and monitoring accounts are the owner's to add; with them added, the release workflow deploys without a code change. See [Deployment-ready status](#deployment-ready-status-and-what-the-owner-adds).

## Architecture

```text
 browser ──► web (Next.js 16) ──► api (NestJS 12 on Fastify)  ──► PostgreSQL 17 (public + pgboss schemas)
                                        │  enqueue (pg-boss)                ▲
                                        ▼                                   │
                                   worker (pg-boss consumers, FFmpeg) ──────┘
                                        │ sealed keys, signed URLs
                                        ▼
                      object storage (Cloudflare R2; MinIO locally)    OpenAI · WaveSpeed (users' own keys)
 backup service ──► encrypted dump + media/ledger mirror ──► backup bucket        monitor ──► alerts, heartbeats
```

- **One database, one queue.** PostgreSQL holds the data and the pg-boss job queues; there is no separate broker. Roles are separate per process: `app_migrator` owns the schema, `app_api` and `app_worker` have only the grants they need, `app_backup` is read only.
- **Layers** (`apps/api/src/modules/<module>`): domain, application, infrastructure, transport; dependency boundaries are checked by `scripts/ci/layers.sh`. Modules: audit, brief, campaigns, identity, lifecycle, media, production, provider-keys, reporting, usage.
- **Contract first.** `packages/contracts/openapi.yaml` is the API contract; generated clients and the contract check (`scripts/ci/contract.sh`) keep the web and the api in step.
- **Secrets by process.** Each process holds only its own secret set and refuses to start (exit 78, naming the key) with a secret it must not hold. The KEK private key lives only in the worker; no admin or support path can read a stored provider key.
- **Release.** One image per service, built once and deployed by digest to one named environment through a locked job (`docs/ops/release.md`).

## Quick start: one stack on your machine

The full, explained version with expected output is [RUN-GUIDE.md](RUN-GUIDE.md). In short, from a clean clone (no account, database URL or credential is needed):

```bash
git clone https://github.com/zainnaeem28/meta-ads.git
cd meta-ads
git checkout dev
corepack enable
pnpm install --frozen-lockfile

# 1. per-process local configuration with throwaway key material (git-ignored)
node scripts/ci/config-consistency.mjs --local-env .env.local.d

# 2. PostgreSQL 17, MinIO, provider stubs, mail stub
docker compose -f docker/compose.dev.yml up -d
until docker compose -f docker/compose.dev.yml exec -T postgres pg_isready -U postgres -d shroomap_dev; do sleep 2; done
```

```bash
# 3. database roles (once per volume) and the per-process database override files
docker compose -f docker/compose.dev.yml exec -T postgres psql -U postgres -v ON_ERROR_STOP=1 <<'SQL'
CREATE ROLE app_migrator LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE PASSWORD 'shroomap-local';
CREATE ROLE app_api      LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE PASSWORD 'shroomap-local';
CREATE ROLE app_worker   LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE PASSWORD 'shroomap-local';
CREATE ROLE app_backup   LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION NOBYPASSRLS CONNECTION LIMIT 2 PASSWORD 'shroomap-local';
ALTER ROLE app_backup   SET default_transaction_read_only = on;
ALTER ROLE app_migrator SET search_path = public;
ALTER ROLE app_api      SET search_path = public;
ALTER ROLE app_worker   SET search_path = public;
ALTER DATABASE shroomap_dev OWNER TO app_migrator;
REVOKE CONNECT ON DATABASE shroomap_dev FROM PUBLIC;
GRANT CONNECT ON DATABASE shroomap_dev TO app_api, app_worker, app_backup;
SQL
docker compose -f docker/compose.dev.yml exec -T postgres psql -U postgres -d shroomap_dev -v ON_ERROR_STOP=1 -c 'ALTER SCHEMA public OWNER TO app_migrator'
echo 'DATABASE_URL=postgres://app_api:shroomap-local@localhost:5432/shroomap_dev'        > .env.local.d/db-api.env
echo 'DATABASE_URL=postgres://app_worker:shroomap-local@localhost:5432/shroomap_dev'     > .env.local.d/db-worker.env
echo 'MIGRATION_DATABASE_URL=postgres://app_migrator:shroomap-local@localhost:5432/shroomap_dev' > .env.local.d/db-release.env
echo 'BACKUP_DATABASE_URL=postgres://app_backup:shroomap-local@localhost:5432/shroomap_dev'      > .env.local.d/db-backup.env
# 4. build (the web build inlines NEXT_PUBLIC_* from web.env)
( set -a; . .env.local.d/web.env; set +a; pnpm build )
# 5. migrate, queues, seed (RUN-GUIDE.md section 6)
( set -a; . .env.local.d/db-release.env; set +a; CI=1 pnpm --filter @shroomap/api db:migrate )
( cd apps/api && node --env-file=../../.env.local.d/release.env --env-file=../../.env.local.d/db-release.env dist/database/jobs-migrate.js )
( cd apps/api && node --env-file=../../.env.local.d/release.env --env-file=../../.env.local.d/db-release.env dist/database/seed.js --dataset=reference )
```

Then run the three processes, one terminal each, and check them (`/health/ready` must answer 200):

```bash
# api (http://localhost:4000)
cd apps/api && node --env-file=../../.env.local.d/api.env --env-file=../../.env.local.d/db-api.env dist/main.api.js

# worker (jobs, media sanitising, provider calls, assembly, erasure)
cd apps/api && node --env-file=../../.env.local.d/worker.env --env-file=../../.env.local.d/db-worker.env dist/main.worker.js

# web (http://localhost:3000)
cd apps/web && node --env-file=../../.env.local.d/web.env node_modules/next/dist/bin/next start -p 3000
curl -s -o /dev/null -w 'live %{http_code}\n'  http://localhost:4000/health/live
curl -s -o /dev/null -w 'ready %{http_code}\n' http://localhost:4000/health/ready
curl -s -o /dev/null -w 'protected route without a session %{http_code}\n' http://localhost:4000/api/v1/campaigns
curl -s -o /dev/null -w 'web sign-in %{http_code}\n' http://localhost:3000/sign-in
```

The api answers on `http://localhost:4000`, the web on `http://localhost:3000`; the sign-in page prints the local password and second-step code. Expected results and every explanation: [RUN-GUIDE.md](RUN-GUIDE.md).

Stop the stack with `docker compose -f docker/compose.dev.yml down` (`-v` also deletes its data).

## Configuration

Every variable lives in `config/registry.json` (the single source). `.env.example` and `docs/ops/secrets.md` are **generated** from it by `node scripts/ci/config-consistency.mjs --write`, and the same script fails when the registry and the api's Zod schema (`apps/api/src/platform/config/registry.ts`) disagree on a name, class, requirement or default. Do not edit `.env.example` by hand; edit the registry and regenerate.

How a process gets its values: locally, `node scripts/ci/config-consistency.mjs --local-env .env.local.d` writes one env file per process (`api.env`, `worker.env`, `web.env`, `release.env`, `backup.env`, `monitor.env`) with harmless defaults and generated throwaway keys; in a hosted environment the host secret store injects them under `shroomap/<env>/<service>/<KEY>`. A process validates its configuration at start and exits 78 naming the key (never the value). Classes: `public` is a setting, `secret` never enters a log, a ticket or the repository. A secret outside a process's own set is refused.

Every variable of `.env.example`, grouped as in the file. **Where to get it** names the account or procedure that supplies a real value; `local` values in `.env.example` are never real credentials.

## Migrations and seeds

- **Migrations** are generated, never written by hand or pushed: `pnpm --filter @shroomap/api db:generate --name=<NNNN>_<ticket>-<slug>` (the number is the ticket's reserved range number), applied with `pnpm --filter @shroomap/api db:migrate` as `app_migrator`. `scripts/ci/lint-db.sh` forbids `drizzle-kit push`. The history, an upgrade from the previous release's snapshot, the compensating-migration rollback check and the seed rerun are checked by `pnpm --filter @shroomap/api db:check-history`. Expand then contract: the previous application must keep working on the new schema for one release.
- **Queues**: `jobs:migrate` installs the pg-boss schema and creates every queue (run after `db:migrate`).
- **Seeds**: `db:seed --dataset=reference|development|staging`, idempotent. `reference` runs everywhere; `development` and `staging` only in their own `APP_ENV`; production accepts `reference` only.
- Local order and commands: [RUN-GUIDE.md](RUN-GUIDE.md) sections 4 and 6.

## Deployment-ready status and what the owner adds

## Troubleshooting

The table in [RUN-GUIDE.md](RUN-GUIDE.md) section 12 lists the symptoms seen on a clean clone with their fixes. Most common: the database roles are missing (step 4), `DATABASE_URL` is set in your shell (`unset DATABASE_URL`), or a port (4000, 3000, 5432) is taken. ## Contributing

`main` holds releases only; `dev` holds all integrated work; each ticket gets its own `feature/<ID>-<slug>` or `bugfix/<ID>-<slug>` branch cut from the latest `origin/dev`. Before submitting: merge `origin/dev`, then run `scripts/ci/submit-check.sh --base origin/dev` (it runs the same wrappers as the pipeline and writes the report the review reads). A change that touches a generated file (`.env.example`, `docs/ops/secrets.md`, the generated clients) is made at its source. Every change is reviewed by someone other than its author. Never commit a secret; gitleaks runs on every ticket range and a finding blocks.
